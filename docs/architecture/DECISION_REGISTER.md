## 1. Status Lifecycle Taxonomy

To prevent conflating architectural design sign-off with code implementation or runtime test execution, every decision in this register uses the following strict status taxonomy:

| Status | Meaning |
| :--- | :--- |
| **`PROPOSED`** | Option has been analyzed and recommended, awaiting human architect decision. |
| **`DISCUSSION`** | Under active design debate or trade-off evaluation. |
| **`DESIGN_ACCEPTED`** | Architecture design is frozen and approved as the engineering baseline; implementation has not yet been completed or verified at runtime. |
| **`IMPLEMENTED`** | Code, database schema, or infrastructure configuration has been implemented in the repository, but full runtime/load/chaos verification is still pending. |
| **`TEST_VERIFIED`** | Implemented and empirically verified by automated unit, integration, concurrency, chaos, or performance tests in CI/CD. |
| **`NEEDS_EVIDENCE`** | Contains empirical performance, recall, latency, or runtime concurrency claims that must be proven by benchmark or integration test execution in `M1–M7`. |
| **`SUPERSEDED`** | Replaced by a simpler or more accurate architectural decision in a subsequent review. |

## 3. Deep Architecture Challenge Decisions (`CH-01` – `CH-07`)

| ID | Decision Summary | Status | Rationale | Consequences & Security/Operational Constraints | Related ADR | Related Requirements | Runtime Evidence Still Required (`NEEDS_EVIDENCE`) | Blocks Implementation? |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **`CH-01`** | **Flash Sale Concurrency, Imperative `SECURITY DEFINER` Procedures & Least-Privilege Table Encapsulation**:<br>1. Encapsulate all 8 Flash Sale DB mutation paths (`fn_mp01`–`fn_mp08`) as imperative PL/pgSQL `SECURITY DEFINER` stored procedures owned by a non-login, non-superuser role (`promotion_proc_owner NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE`) with fixed `SET search_path = pg_catalog, public`.<br>2. Revoke direct `INSERT, UPDATE, DELETE, TRUNCATE` on `flash_sale_campaigns`, `flash_sale_claims`, and `flash_sale_items` from `promotion_app_role` (which in PostgreSQL also blocks direct `SELECT ... FOR UPDATE/SHARE`), and grant explicit `EXECUTE` only on the approved procedures.<br>3. Enforce strict topological lock acquisition order inside every procedure: `1. flash_sale_campaigns (FOR SHARE/UPDATE) -> 2. flash_sale_claims (by claim_id ASC) -> 3. flash_sale_items (by sku_id ASC) -> 4. outbox_messages -> 5. idempotency_records`.<br>4. Retain non-locking witness triggers (`trg_verify_claims_campaign_prelocked`, `trg_verify_items_campaign_prelocked`) strictly as an accidental-bug guard for privileged maintenance scripts, never as an access-control boundary. | **`DESIGN_ACCEPTED`** | Eliminates PostgreSQL CTE join reordering, prevents reverse `Table 2 -> Table 1` trigger deadlocks, blocks application-role direct DML bypasses at the PostgreSQL ACL layer, and guarantees via `FOR SHARE` vs. `FOR UPDATE` mutual exclusion that no old-epoch transaction can commit after `fn_mp07_rebuilder_fence_and_snapshot` acquires `FOR UPDATE` on `flash_sale_campaigns`. | - **True Security Boundary**: PostgreSQL ACL revocation (`REVOKE INSERT, UPDATE, DELETE` from `promotion_app_role`) + non-superuser `SECURITY DEFINER` ownership (`promotion_proc_owner`).<br>- **Custom GUC Witness Limitation**: `promotion.locked_campaign_<uuid>` is session-writable by any role that already possesses direct table DML privileges; witness triggers protect against accidental lock-order bugs inside privileged functions/scripts, **not** against a malicious role with direct table DML rights.<br>- **Migration/Admin Exception**: `promotion_migrator_role` runs schema migrations at deployment only; break-glass DBA sessions are audited. | [`ADR-0005`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0005-flash-sale-concurrency-and-three-tier-locking.md) | `FR-PRO-001` to `FR-PRO-005`, `NFR-SEC-003`, `NFR-REL-001` | Runtime Testcontainers verification of ACL denial (`SQLSTATE 42501`), lock ordering, Writer/Reconciler race, and Redis rebuild (`SPEC-CH01-T1` to `T6` in `M3` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-02`** | **Orthogonal `Order` & `PaymentAttempt` State Machines & Non-Fabricated Provider Facts**:<br>1. Separate `Order` lifecycle from `PaymentAttempt` lifecycle (`1:N` attempts per order).<br>2. Deduplicate webhooks via `payment_webhook_logs (provider_event_id PK)` in the same DB transaction as `payment_attempts`, `refund_requests`, and `outbox_messages`.<br>3. Store provider-reported timestamps (`provider_authorized_at`, `provider_captured_at`, `provider_voided_at`, `provider_refunded_at`) separately from internal transition timestamps; never fabricate `provider_authorized_at` when only a capture webhook arrives.<br>4. Late capture after order expiry or `VOID_PENDING`/`VOIDED` atomically inserts into `refund_requests (UNIQUE (attempt_id, reason_code))` and triggers an idempotent auto-refund. | **`DESIGN_ACCEPTED`** | Financial payment states (`CAPTURE` vs. `VOID` vs. late `CAPTURE` after `VOID`) form a branching graph that cannot be modeled by a scalar rank, and audit compliance forbids fabricating provider timestamps. | Requires atomic single-transaction processing of webhook log insertion, attempt transition validation, refund request creation, and Outbox emission in `payment-service`. | [`ADR-0004`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0004-hybrid-order-fulfillment-saga-orchestration.md) | `FR-ORD-001` to `FR-ORD-004`, `FR-PAY-001` to `FR-PAY-005`, `NFR-REL-002` | Runtime verification of out-of-order, duplicate, missing, and contradictory webhooks (`SPEC-CH02-T1`, `T2` in `M3` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-03`** | **Two-Class HTTP Idempotency with `lease_generation` Fencing & Downstream Reconciliation**:<br>1. Class A (pure local DB + Outbox) relies on single-transaction PostgreSQL atomicity.<br>2. Class B (external side effects: Redis Lua, Payment Provider) assigns an immutable `downstream_operation_id` at `lease_generation = 1`.<br>3. Local `WHERE lease_generation = :expectedGen` fences local DB state, while passing `downstream_operation_id` (and `lease_generation` for Redis Lua) deduplicates at the downstream provider.<br>4. Expired leases transition to `RECONCILING` (never blind retry). Type I (authoritative read-after-write + idempotent) `NOT_FOUND` resumes with the same `downstream_operation_id`; Type II (eventually consistent / non-idempotent) `NOT_FOUND` polls in `RECONCILING` and escalates to `MANUAL_INTERVENTION_REQUIRED` after `15m`. | **`DESIGN_ACCEPTED`** | A local database lock/lease cannot physically stop a paused OS thread from flushing an already-prepared TCP packet to an external system, nor does an expired lease prove the external call failed. | All internal platform services (`Inventory`, `Promotion`, `Payment Simulator`) must be implemented as Type I downstreams (strongly consistent lookup by `downstream_operation_id`). | [`ADR-0003`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0003-transactional-outbox-and-inbox-idempotency.md) | `FR-IDEM-001` to `FR-IDEM-004`, `NFR-REL-003` | Runtime fault-injection tests for timeout reconciliation and stale worker fencing (`SPEC-CH03-T1` in `M1/M3` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-04`** | **Pragmatic At-Least-Once Transactional Outbox & Consumer-Enforced Aggregate Version Ordering**:<br>1. **Delivery Contract**: At-least-once delivery with `partition_key = aggregate_id`. Duplicate publication and out-of-order Kafka log appends across stale/competing relay processes are explicitly expected and tolerated.<br>2. **Relay Behavior**: Coordinated via PostgreSQL shard leases (`outbox_relay_shards`); each cycle claims **at most one event (the lowest unpublished `aggregate_version`) per `aggregate_id`** (`DISTINCT ON (aggregate_id)`) and publishes with standard idempotent Kafka producers (`acks=all`, `enable.idempotence=true`). Complex per-generation `transactional.id` broker-fencing loops are removed (`SUPERSEDED`).<br>3. **Consumer Contract (Where Strict Ordering & Correctness Live)**: Consumer Inbox deduplication (`inbox_messages`) and aggregate state updates execute in **one atomic PostgreSQL transaction**. Consumers apply **only** `incoming.aggregate_version == last_applied_version + 1`:<br>   • `<= last_applied_version`: treated as stale/duplicate (idempotent no-op).<br>   • `> last_applied_version + 1`: deferred/retried via retry topic until the missing version arrives (never silently skipped). | **`DESIGN_ACCEPTED`** | A PostgreSQL lease cannot fence an already-running Kafka producer across an asynchronous network without complex broker transaction coordination, whereas stateful consumers **already** require atomic `inbox_messages` + `last_applied_version + 1` validation to handle DLQ replays and retries. Placing the strict ordering invariant at the Consumer application boundary achieves 100% aggregate state correctness with dramatically simpler producer infrastructure. | Clearly separates:<br>1. **Kafka Delivery Order**: Best-effort ordered (`partition_key = aggregate_id`), may contain duplicates or `[v1, v2, v1]` under relay lease steal.<br>2. **Consumer Application Order**: Strictly sequential (`v1 -> v2 -> v3`) enforced by `incoming.version == last_applied_version + 1`.<br>3. **Aggregate State Correctness**: 100% deterministic per aggregate. | [`ADR-0003`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0003-transactional-outbox-and-inbox-idempotency.md), [`ADR-0010`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0010-event-contracts-json-schema-and-kafka-kraft.md) | `FR-OUT-001` to `FR-OUT-004`, `NFR-REL-004` | Runtime integration tests for duplicate delivery, `[v1, v2, v1]` stale replay discard, and `[v1, v3, v2]` gap deferral/recovery (`SPEC-CH04-T1` to `T3` in `M1/M3` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-05`** | **OIDC / RFC 9068 Access-Token Validation & Principal-Type Separation**:<br>1. Reject OIDC `id_token` (`aud = "commerce-web-spa"`) at API Gateway and all Resource Servers (`401`).<br>2. Separate `HUMAN_PRINCIPAL` from `SERVICE_PRINCIPAL` (`client_credentials` tokens strip all human roles `CUSTOMER`/`ADMIN_*`).<br>3. Extract service roles strictly from `resource_access[target_service_id].roles` (never a flat union across services). | **`DESIGN_ACCEPTED`** | Prevents horizontal privilege escalation across services and prevents M2M service accounts from invoking customer/admin endpoints. | Every microservice configures its own `EXPECTED_AUDIENCE` / `SERVICE_ID` in its JWT validation middleware. | [`ADR-0006`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0006-api-gateway-yarp-and-oidc-jwt-security.md) | `NFR-SEC-001`, `NFR-SEC-002` | Security integration tests with forged/cross-service JWTs (`SPEC-CH05-T1` in `M1/M2` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-06`** | **Search (`PostgreSQL FTS`) & `pgvector` Generation-Isolated Retrieval**:<br>1. Use PostgreSQL 17 FTS initially and `pgvector` for RAG embeddings.<br>2. Enforce `pgvector` physical HNSW index limits in schema (`<= 2,000d` for FP32 `vector_cosine_ops`; `2,001d..4,000d` for FP16 `halfvec_cosine_ops`).<br>3. Isolate embedding migrations via `embedding_index_generations` (`provider_name`, `model_id`, `model_version`, `dimensions`, `index_storage_type`, `is_active_for_search`). | **`DESIGN_ACCEPTED`** | Prevents mixed-model vector space corruption and respects PostgreSQL 8 KB index page limits for `3072d` embeddings. | Latency (`p95 < 50ms`) and recall (`Recall@10 >= 0.95`) remain empirical benchmark objectives (`NEEDS_EVIDENCE`), not pre-verified facts. | [`ADR-0007`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0007-catalog-search-postgresql-fts-vs-opensearch.md), [`ADR-0008`](file:///home/anhltn/projects/distributed-commerce-platform/docs/adr/ADR-0008-ai-agent-security-boundary-and-pgvector-rag.md) | `FR-CAT-003`, `FR-AI-003`, `NFR-PERF-001`, `NFR-PERF-002` | Empirical `k6` FTS benchmark (`M2`) and `pgvector` recall/latency benchmark (`M5/M7` — `NEEDS_EVIDENCE`). | **No** |
| **`CH-07`** | **Triple-Gated Chaos Fault Injection & Fail-Closed Production Guard**:<br>1. Production startup fails closed (`FatalSecurityConfigurationException`) if `(ENVIRONMENT == 'production' OR PRODUCTION_LOCK == 'true') AND FAULT_INJECTION_ENABLED == true`.<br>2.
